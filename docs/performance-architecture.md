# 小镇游戏性能架构升级方案

> **状态**：Draft，待实施与真实设备验证；本文不代表升级已经完成。
> **版本与日期**：v1，2026-10-05。
> **基线**：当前工作区的 `performance-v6` 场景与 Three.js 0.180.0。
> **相关代码**：[主循环](../src/main.js)、[渲染管线](../src/rendering.js)、[光照](../src/lighting.js)、[水面](../src/water.js)、[导航与交互](../src/interaction.js)、[性能策略](../src/performance-policy.js)。
> **交叉参考**：[总体架构](./architecture.md)、[第六版性能验证](./performance-verification.md)、[原始采样](./performance-samples-v6.json)、[画面验证](./visual-verification.md)、[项目说明](../README.md)。

## 文档定位与结论

本方案解决当前三维场景的持续帧率、点击寻路卡顿与后续场景扩大的性能问题，是总体架构方案的客户端性能补充。多人服务器、经济事务和存档继续遵循总体架构，本方案不重新定义这些系统。

优先研究静态与动态光照分离、街区分块与 LOD，其次是跨房屋实例化、模拟与渲染解耦、导航缓存。先建立可复现的真实设备基线，再根据分项耗时选择实施顺序。每项升级应能独立比较和回退。

收益方向来自代码分析，具体 FPS、可承载实体数和耗时改善尚未测得。Vite 与 TypeScript 迁移改善依赖管理和工程边界，但不能作为持续帧率提升的证明。将计算移入 Web Worker 也不能直接消除 GPU 绘制成本。

## 当前事实与性能假设

### 已有措施

| 当前实现 | 代码依据 | 仍需解决的问题 |
| --- | --- | --- |
| 普通画面统一由一个 RAF 调用合成管线 | `main.js`：`animateTraffic`、`render` | 一次合成内部仍有多个渲染阶段，不能理解成只有一次 GPU 绘制 |
| 每栋房屋按材质合并部件，其他房屋通过克隆共享几何和材质 | `house.js`：`mergeStatic`；`main.js`：`house.clone(true)` | 房屋之间仍各自提交绘制；共享资源不等于跨房屋合批 |
| 树木、庭院植物、信号灯使用 InstancedMesh | `landscape.js`：`instances`；`traffic-signals.js`：`batch` | 较大批次以整体边界参与裁剪，局部不可见实例仍可能参与绘制 |
| 手机布局像素比上限 1.5，其他布局上限 2 | `lighting.js`：`configureRenderer`；`main.js`：`compact` | 档位由视口宽度选择，并非根据实际设备 GPU 能力选择 |
| 2048×2048 VSM 阴影，普通连续更新限于 30 Hz | `lighting.js`；`rendering.js`：`shadowGate` | 限频仍需要周期性绘制投影物；没有独立的静态光照资产 |
| 手机布局 384、其他布局 512 的反射目标，更新上限 12/18 Hz | `water.js`：`createWater` | 更新时仍需额外绘制反射视角；细小装饰可使用更简单表现 |
| RenderPass、SSAOPass、OutputPass，AO 分辨率随档位降低 | `rendering.js`：`createRendering` | AO 需要法线与深度阶段及屏幕处理，存在持续成本 |
| 四级自适应画质，先降低 AO 再降低渲染比例 | `performance-policy.js`：`createQualityController` | 只能缓解负载；比较升级收益时需锁定相同画质 |
| 每次点击在 79×79 网格进行 BFS | `interaction.js`：`findWalkPath` | 新建搜索数组，障碍查询反复遍历树木和房屋 |
| 夜间每帧按角色距离排序路灯并启用最近 4/8 盏 | `main.js`：`animateTraffic` | 可在位置或灯具变化后更新；当前数量下收益须实测 |

在 Three.js r180 中，SSAOPass 读取已有颜色结果，另行生成法线和深度，再计算、模糊和合成 AO。因此 `RenderPass + SSAOPass` 不是重复绘制同一份颜色的错误；不能直接删除 RenderPass。优化对象是各阶段参与绘制的几何、像素量和效果计算。[r180 SSAOPass 源码](https://github.com/mrdoob/three.js/blob/r180/examples/jsm/postprocessing/SSAOPass.js)

### 证据范围

第六版验证报告已记录普通 RAF 从两次合成降为一次，以及刷新策略、截图恢复、进出屋和自适应档位的检查。报告中的浏览器 RAF 间隔受到节流；CPU 提交耗时也不等于 GPU 执行时间。这里引用已有报告，不将其视为本次重新执行的测试。

以下判断是待验证假设：阴影、AO 和倒影可能是主要持续渲染成本；分块和 LOD 可能减少多个阶段的几何负载；缓存导航可能改善点击瞬间的主线程停顿。尚未确定三者在目标设备上的占比。

## 目标与边界

沿用总体架构的参考桌面验收起点：规定设备、浏览器、1080 像素纵向分辨率与最大首版场景下，目标稳定 30 FPS，帧间隔 p95 不超过 50 ms；较好设备以 60 FPS 为目标。手机必须另外指定实体设备与画质档位，不通过视口模拟推导性能。

改善性能时保留昼夜、角色跟随、交通停车、点击行走、进出屋、屋顶隐藏和 PNG 导出。细节简化及烘焙效果需要同视角画面对照；不能只凭降低分辨率后的 FPS 判定架构升级成功。

首轮沿用 Three.js 与 WebGL，不引入完整 ECS、独立物理引擎或全面 WebGPU 重写。现有程序化资产继续使用，只为经过测量的瓶颈增加必要模块。

## 测量基线与决策方法

### 可复现采样

每种目标设备记录设备型号、浏览器版本、电源模式、显示刷新率、视口、实际画布分辨率、像素比、质量档位、地图版本及代码版本。页面保持前台，加载和 shader 首次编译完成后预热 20 秒，每个场景采样 60 秒，至少重复三次。手机追加连续运行约十分钟的热稳定检查。这些时长是拟议测试条件。

固定镜头位置、道路点击路线、昼夜和画质。先使用锁定档位比较架构差异，再启用自动画质检查实际体验。设备切后台、截图、窗口缩放和首次资源加载单独标注；日常前台运行中的真实慢帧不能随意剔除。

| 场景 | 主要观察点 |
| --- | --- |
| 白天静止、白天行走、连续旋转 | 阴影、AO、反射和相机更新成本 |
| 夜间行走 | 点光源与路灯选择成本、边界切换闪烁 |
| 进屋、室内转向窗口、出屋 | 室外可见性、屋顶状态与恢复峰值 |
| 连续远距离点击及不可达目标 | 寻路耗时、内存分配、输入响应 |
| 近景、远景和街区边界反复移动 | 分块裁剪、LOD 切换、批次数量 |
| 昼夜切换与截图导出 | 缓存失效、立即刷新、尺寸和档位恢复 |

### 指标与分项实验

| 指标 | 定义与用途 |
| --- | --- |
| frameInterval p50/p95、平均 FPS、慢帧数量 | 主 RAF 间隔；同时记录实际帧时间分布 |
| simulationMs、navigationMs、presentationMs | 用性能时钟记录 CPU 系统执行，不包含 GPU 执行时间 |
| renderSubmitMs | CPU 执行渲染调用的时间；当前 `lastSubmitMs` 属于此项 |
| GPU 分项时间 | 仅在设备提供有效 GPU 计时能力时采集；不支持时明确缺测 |
| drawCalls、triangles、各阶段更新次数 | 当前 `renderer.info` 汇总不能直接当成主颜色阶段的独立统计 |
| 批次数、可见街区数、各 LOD 实例数 | 判断分块和实例化是否产生预期效果 |
| RenderTarget 尺寸、资源数量、长期内存变化 | 判断效果缓存和反复进出屋是否积累资源 |

在相同路线和锁定档位下，分别关闭 AO、反射、阴影做单因素比较。记录帧时间和画面变化，而非简单将各项 FPS 差值相加。需要逐阶段计数和计时时，在渲染管线增加诊断钩子。

若降低渲染分辨率明显改善帧时间，优先研究像素与效果成本；若寻路或模拟占用主线程，优先处理 CPU 系统；若调用数高且批处理实验有效，推进实例化。以上是诊断线索，最终结合 GPU 计时或性能分析确认。

## 模块职责与更新顺序

以下模块和名称为目标设计，尚未存在于当前项目。

| 模块 | 职责 | 依赖边界 |
| --- | --- | --- |
| FrameScheduler | 一个 RAF、固定步长、插值与后台恢复 | 不执行业务交易 |
| WorldState / EntityViewRegistry | 逻辑实体状态到模型、实例索引的映射 | 世界数据不保存 Mesh |
| ChunkManager / VisibilitySystem | 街区边界、每个视角的可见集、LOD | 不删除权威状态或导航障碍 |
| StaticLightingCache | 烘焙资源、版本、失效与回退 | 与动态阴影明确组合规则 |
| RenderPipeline | 颜色、AO、反射、阴影、输出与截图 | 统一管理 RenderTarget 和诊断 |
| NavigationGrid / PathService | 通行缓存、搜索、请求版本与取消 | 不依赖 DOM 或 Three.js |
| ResourceCache | 几何、材质、贴图的共享和释放 | 共享资源仅由所有者释放 |

每帧先收集输入和外部状态变化，执行有界的固定步长模拟，再更新插值后的角色和相机、各视角可见集与细节等级，最后调度效果更新并绘制。水波等纯表现动画按显示时间更新。截图进入同一渲染管线，通过临时配置完成后恢复状态。

模块提供最小的 update、invalidate、dispose 接口。尺寸变化、昼夜、门和屋顶显隐通过明确事件失效缓存，逐步替代每帧扫描对象属性。dispose 清理事件、观察器、计时器、Controls 和渲染资源，以兼容总体架构的生命周期方案。

## 静态与动态光照分离

### 方案

先选一个街区验证静态遮蔽资产，随后研究固定日光投影。固定建筑与地形使用 lightmap、AO 贴图或程序化接触遮蔽；人物、车辆、活动门等保留动态表现。昼夜保留独立的颜色和强度配置，必要时使用两个状态的静态光照资源。

当前所有物体共享实时阴影路径。仅设置 `shadowMap.autoUpdate=false` 再手动更新，并不会自动形成两套静态和动态阴影。组合静态遮蔽和动态投影可能需要材质适配，必须验证重复变暗、人物投影和建筑遮挡动态物体的效果。[Three.js 阴影机制](https://threejs.org/manual/pages/shadows.html)

首个原型只替代固定的局部遮蔽；效果满意后，在低性能档评估减少或关闭实时 SSAO，高性能档保留实时效果作为对照。是否扩大到静态日光阴影由分项测量决定，避免直接承诺整条阴影通道都能移除。

### 缓存与失效

缓存键包含几何/地图版本、材质效果版本、光照模式与烘焙质量。程序化建筑若改比例或增加窗洞，旧资源不能继续复用。需要光照 UV 的资产单独建立生成流程，不假设现有几何已经满足要求。

“静态”指缓存有效期内不变化。后续砍树、建造、家具移动会影响遮蔽；先标记受影响街区失效，切回实时或简化效果，再按预算重建。不能同步重算整镇造成新的长帧。

门打开与屋顶隐藏可能改变室内外投影。首轮保留这些部件的实时路径，或为相关房屋禁用已失效的烘焙贡献；恢复原状态后再复用有效缓存。每种切换都需要室内、窗边和出屋截图验证。

## 街区分块、可见性与 LOD

以现有街区为第一版空间单元。每个块保存边界、房屋和植物批次、简化模型、交互代理与缓存版本；块大小通过绘制调用和裁剪收益比较确定，不直接把每株植物变成独立对象。

| 表现层级 | 拟议内容 | 保留的能力 |
| --- | --- | --- |
| 近景 | 窗框、花箱、草叶、细瓦纹 | 完整点击、开门和室内表现 |
| 中景 | 简化窗框与植物，减少小装饰 | 房屋轮廓、门口、昼夜颜色 |
| 远景 | 简化建筑和树冠，移除细小装饰 | 街区布局与背景轮廓 |
| 当前视角不可见 | 跳过该视角的几何提交 | 逻辑模拟、碰撞和其他视角所需表现 |

LOD 优先按屏幕占比选择，并设置进入/退出阈值的滞回，避免缩放时来回切换。第一轮让所有资源驻留，只验证裁剪与细节切换；扩大地图后再增加加载、卸载和内存预算。

可见性按渲染视角分别计算。主相机看不见的树可能出现在湖面倒影中，也可能向可见道路投影，不能依据主相机结果全局设置 `visible=false`。反射视角可使用简化模型并省略微小装饰；阴影视角保留必要投影物。

进屋后按室内空间和窗口/门口可见范围减少室外绘制，先用保守规则保留可能可见的邻近街区。不能直接隐藏整个室外场景导致窗外空白。裁剪只改变表现，不移除树木和建筑的导航障碍。

## 跨房屋实例化与交互映射

当前九栋房屋共用几何和材质，但克隆出的 Mesh 仍分别绘制。实例化进一步将相同几何和材质的多个房屋部件放入批次。[Three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)

批次键建议为街区、几何类型、材质、LOD 和阴影配置。跨街区无限合并会削弱裁剪；批次过碎又增加调用，需要比较实际镜头下的总成本。

先实例化墙体、窗框等固定部件，门保持独立动画对象。首轮屋顶保持可独立隐藏的对象，后续只有在其调用成本明确时再增加实例显隐管理；不假设普通 InstancedMesh 已经提供所需的逐实例 visible 属性。

EntityViewRegistry 保存 entityId 到批次、instanceIndex 和交互代理的映射。射线命中实例或简化代理后恢复房屋 ID；增删和重新分批时更新映射，避免点错房屋。室内家具与门使用独立实体，不依附合并后的装饰几何。

资源缓存统一持有几何、材质和纹理。移除一栋房屋或卸载一个街区时不能释放其他实例还在使用的资源。截图和材质主题切换也必须覆盖所有批次。

## 模拟与渲染解耦

客户端交通模拟先验证 30 Hz 固定步长，画面根据前后状态插值按 RAF 刷新。此频率是原型起点，不是服务端网络频率；总体架构中多人 10 Hz 同步由独立协议和插值缓冲处理。

模拟使用独立逻辑状态，不直接将 Mesh 坐标作为唯一事实。当前车辆 delta 上限为 0.05 秒，低帧率时会截掉时间；迁移后明确有界补算与恢复策略，避免无上限补跑，也避免把缓慢移动误当成优化成功。建议每帧补算上限先验证五步，后台恢复时重置表现缓冲。

交通信号与车辆停止规则共享模拟时间。插值跨越停止线、停车和环路重置时采用明确边界，不能让视觉插值穿过红灯或从地图一端扫到另一端。车轮只在有效位移变化时更新，水波保留每帧 uniform 更新。

路灯选择在角色移动超过阈值、切换昼夜或灯具布局变化后重算；灯组边界加入滞回，避免来回闪烁。阈值通过夜间行走验证；当前数量较少，先测量再决定是否引入空间索引。

## 导航缓存与按需使用 Web Worker

### 缓存与搜索

提取共同的地图、房屋占地、树木与水域障碍定义，生成 79×79 的 Uint8Array 通行网格。每次搜索用数组查询替代重复遍历所有障碍；以 mapVersion 和 obstacleVersion 标识有效性。

初始化时构建静态网格，障碍变化只重算受影响区域。人物半径、房门接近点、边界和禁止斜穿障碍的规则沿用现有行为，湖面美术轮廓与碰撞定义逐步统一。渲染 LOD 或街区不可见不会改变网格。

先保留 BFS 作为行为对照，缓存生效后再比较 A*。若斜向步长采用不同代价，需要定义目标是最少步数还是最短几何距离，并匹配启发式；不能只替换算法名称就宣称更快或路径相同。

复用 parents、队列及访问标记，重置方式由搜索规模实测决定。路径先用坐标或网格索引返回，再转换为表现用向量，避免纯导航依赖 Three.js。

### Worker 引入条件

缓存后，若实际点击仍产生明显长任务，或多人/NPC 增加并发请求，再将纯 PathService 移到 Web Worker。当前一个角色不预设 Worker 一定优于主线程，消息传递和初始化也有成本。

请求携带 requestId、起终点、地图与障碍版本；结果回传路径及相同版本。新的点击取消或覆盖旧请求，旧结果不能接替新路线。角色起点已变化时重新校验衔接，障碍版本变化时重算；Worker 内缓存同步通过版本化增量更新。

Worker 故障时提供明确失败或有界主线程回退，不无限堆积路径请求。客户端计算只用于表现与预览，未来服务端仍校验权威移动。

## 渲染策略、截图与资源管理

RenderPipeline 统一管理主颜色、AO、反射、阴影和输出阶段。效果更新同时考虑预算、可见性与失效：湖面不可见时不刷新反射，正常移动仍遵守刷新上限；主题、尺寸和镜头跳转按当前强制更新语义处理。静态视角下车辆仍在运动，不能仅凭相机不动就永久停止更新。

现有自适应画质作为兜底保留。降档先降低效果成本，再降低渲染比例；恢复保留滞回。诊断同时记录用户选择档位、实际档位和实际画布尺寸，避免不同档位下的样本混为同一基线。

当前策略将超过 80 ms 的帧间隔全部排除。这能避开部分后台和截图样本，也可能忽略前台持续低于约 12.5 FPS 的状态；它属于需要验证的策略缺口。后续根据可见性、已知截图/恢复事件区分无效样本，单独覆盖前台持续严重慢帧，不在本文中宣称已修复。

截图使用同一 RenderPipeline，并在 finally 中恢复像素比、合成/AO 尺寸、相机、LOD、效果刷新状态和画质采样。若导出尺寸需要更高细节，临时提升 LOD；不能只放大画布后继续使用低细节模型。资源未准备好时明确等待或沿用当前可用表现。

后台降低或暂停表现更新，恢复时重置时钟与插值；未来网络会话独立维护。反复进出屋、切换昼夜、截图和模块重建应检查 RenderTarget、监听器和共享资源数量趋于稳定。

## 分阶段实施与回退

下表为实施计划，不是本次已完成的代码变更。阶段 B、C 的先后可根据 A 的测量调整；不同时替换全部渲染与交互路径。

| 阶段 | 工作内容 | 验收与回退 |
| --- | --- | --- |
| A：基线与诊断 | 前台真实设备采样、效果开关、分项指标 | 得到可复现基线；明确主要耗时与画质条件 |
| B：分块与 LOD | 植物按块分批、远景简化、每视角可见集 | 可见负载下降且无窗口/倒影/阴影缺失；可切回旧全量场景 |
| C：静态光照原型 | 一个街区静态 AO，随后评估固定阴影 | 降低测得的效果成本、画面对照通过；按块切回实时路径 |
| D：实例化 | 固定房屋部件、ID 映射与资源归属 | 目标阶段调用下降、点击与屋顶行为一致；恢复克隆路径 |
| E：时钟与导航 | 固定步长、插值、路灯失效、障碍缓存 | 交通速度和停车正确、点击峰值改善；保留旧模拟与搜索对照 |
| F：扩大与稳定性 | 必要时 Worker、室内裁剪、长期运行 | 连续运行、快速输入、截图恢复和资源回收通过 |

回退开关按模块设置，开发诊断入口与正常游戏界面分开。每轮只打开待验证项，记录配置；资源缓存失效时先用已验证的回退路径，避免短期性能收益以错误画面为代价。

## 验收与结果报告

| 验证项 | 通过依据 |
| --- | --- |
| 帧率与帧时间 | 同设备、分辨率、档位和路线，报告 p50/p95 与慢帧；达到参考设备预算或明确剩余瓶颈 |
| 收益归因 | 目标阶段耗时或负载确实下降，重复结果超过基线波动；自动降档单独报告 |
| 画面 | 昼夜、近远景、室内窗边、反射与阴影截图对照，记录可接受的简化 |
| 房屋交互 | 九栋可正确点击，门动画和指定屋顶隐藏/恢复不串房 |
| 交通 | 不同显示帧率下速度一致，红黄灯停车、恢复和环路边界正确 |
| 导航 | 湖岸、树木、房屋、斜向角、不可达目标和起终点边界正确 |
| 请求版本 | 快速点击、障碍变化、Worker 返回延迟时只接受当前合法路线 |
| 缓存失效 | 昼夜、建造/移物原型、开门、屋顶和尺寸变化不残留过期效果 |
| 截图 | 导出正确，恢复后像素比、档位、AO、LOD、相机与计时正常 |
| 生命周期 | 反复场景切换和重建后无持续资源增长；共享资源未提前释放 |
| 严重慢帧 | 前台持续长帧得到正确处理；后台恢复和截图不触发无意义降档 |

测试聚焦交通、导航、实例 ID、缓存失效和截图恢复这些易回归行为；纯模块搬迁无需编写重复实现的测试。现有性能策略测试沿用，并在策略改变时补真实边界场景。

每阶段结果报告保存原始采样、设备与配置、版本、画面对照、通过项、未通过项和回退状态。当前第六版报告作为历史基线保留，不能把后续设计或受控输入测试写成真实设备已达标。

## 风险与待测事项

| 风险或未知项 | 处理方式 |
| --- | --- |
| 阴影/AO/反射并非目标设备主瓶颈 | 先做分项测量，再决定原型投入 |
| 烘焙资源增加加载和内存、动态布局难更新 | 单街区验证，版本化缓存，支持局部实时回退 |
| 静态与动态遮蔽重复变暗或遮挡关系错误 | 验证材质组合，不直接叠加两个黑色投影 |
| 分块太细增加调用，太大难裁剪 | 比较街区规模、镜头和各阶段总成本 |
| 主视角裁剪破坏倒影或投影 | 分别计算主相机、反射和阴影视角需求 |
| 实例化增加显隐和点击复杂度 | 固定部件先迁移，门和屋顶保留独立控制 |
| 固定步长使低帧率补算过载 | 有界补算、后台恢复、插值边界验证 |
| Worker 收益小于通信成本 | 导航缓存后测量，再决定启用 |
| 自动画质掩盖比较、长帧过滤遗漏严重卡顿 | 锁档对照，记录实际档位，补前台严重慢帧场景 |
